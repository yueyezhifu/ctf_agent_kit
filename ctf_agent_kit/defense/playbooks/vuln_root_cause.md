# 漏洞成因分析框架（蓝队 playbook）

> 目标：从「发生了什么」追到「为什么会发生」，输出可归因、可修复的根因结论。

## 分析流程

### 1. 事实固定（先取证，后分析）
- 保全原始日志/流量/镜像，计算哈希，记录取证时间线
- 用 `defense/log_analyzer.py` 跑 IOC 扫描 + 攻击时间线，确定入侵路径
- 标注每条结论的证据（日志行号 / pcap 帧号 / 文件偏移）

### 2. 漏洞定位（按层归因）

| 层 | 典型成因 | 排查动作 |
|---|---|---|
| 代码层 | SQL 拼接、危险函数、缺校验 | 定位污点源到汇的完整数据流 |
| 框架/组件层 | 已知 CVE、配置错误 | 版本指纹比对漏洞库 |
| 架构层 | 信任边界缺失、权限模型缺陷 | 画数据流图，标信任边界 |
| 运维层 | 弱口令、暴露面过大、密钥硬编码 | 端口/目录/凭据审计 |

### 3. 根因分类（产出必须落入其一）
- **输入校验缺失**：污点数据未过滤直达危险汇
- **设计缺陷**：机制本身不安全（自研加密、可预测 token）
- **配置错误**：默认口令、调试模式上线、权限过宽
- **依赖漏洞**：第三方组件已知 CVE
- **逻辑缺陷**：越权、条件竞争、业务流程可绕过

### 4. 输出格式（成因分析报告）

```
## 漏洞成因分析
- 漏洞名称/类型:
- 触发路径:（源 → 传播 → 汇，附证据行号）
- 根因分类:（上表五类之一）
- 影响范围:（受影响接口/数据/权限）
- 攻击者实际利用情况:（日志证据：是否已被利用、窃取了什么）
- 修复建议:（引用 remediation.md 对应条目）
```

## 常见误区

- 把「攻击入口」当「根因」：入口是表象，根因是为什么入口能被打穿
- 只修点不修面：同类成因要在代码库全局搜索（grep 同类危险模式）
- 忽略时间线：先确认漏洞引入时间（git blame），评估历史暴露窗口
